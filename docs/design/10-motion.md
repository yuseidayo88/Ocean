# 動き — 速さと、なめらかさ

「押してから反応するまで」と「出てくるときの気持ちよさ」は別の問題。
遅いのを飾りで隠すことはできないので、**先に速くしてから、動きをつけた。**

---

## 1. 押してから反応するまで

### 何が遅かったか

右ペインの開閉・タブの切り替え・ホームのビュー切り替えは、
どれも URL の `?…` を書き換えるだけの操作なのに `router.replace()` を呼んでいた。
App Router はこれを**画面の移動**として扱うので、同じ画面のままでも
サーバーに RSC を取りに行く。

    行を1回押したときに飛ぶ通信:
      /tasks?open=tk-revenue&_rsc=dEtN30yiO4TWHqEl

手もとで 30ms、ネットワーク越しなら数百 ms。
**見せたいものはもう全部クライアントにあるのに、毎回取りに行っていた。**

### 直したかたち

`lib/use-open.ts` の書き換えを `window.history.replaceState` にした。
Next.js は素の history API を `useSearchParams` と同期させるので、これで足りる。

- `useOpen()` — 右ペインの1件（`?open=<id>`）
- `useTabs()` — タブの並びと現在地（`?open=a,b&at=1`）
- `useParam()` — 画面の中の切り替え（ホームの `?view=desk`）

**通信ゼロ。** URL は変わるので、リンクを渡せることも ‹ › が効くことも変わらない。

### 行き先は先に取っておく

左レールの7つの行き先には `prefetch` を明示した。
押してから取りに行くのをやめる。数が7つしかないので、先に取っておける。

## 2. なめらかさ

### 動きの言葉は1つだけ

    EASE      = .3s  cubic-bezier(.32, .72, 0, 1)   ふつう
    EASE_FAST = .16s cubic-bezier(.32, .72, 0, 1)   面の明るさ・文字の色

速く始まってゆっくり止まる（指で押して離した物が止まる形）。
**増やさない。** 画面ごとにイージングを変えると、それだけでバラバラに見える。

### 出入りするもの

| どこ | どうする |
|---|---|
| 左レール | 消さずに**幅を 0 にする**。中身は 260 のまま押し出されるので、文字が畳まれて崩れない。閉じているあいだは `inert` で触れない |
| 右ペイン | `panein` / `paneout` の CSS アニメーション。**閉じるときは畳み終わってから**親に消してもらう（待たせるのは `Pane` の中だけ。画面ごとに書かない） |
| 入力欄 | 書いたぶんだけ伸びるところを滑らかに。高さを測るには一度 0 に落とす必要があるので、**測るあいだだけ動きを止め**、いまの高さに戻してから次の高さへ動かす |
| 質問の板 | `.rise` — 下から少し上がって出る |
| 会社の切り替え・わたし | `.pop` — 押した場所から開く |
| ホームのビュー | `key` を変えて `.rise`。次の面がふわっと出る |

### 出るときは最初のフレームから動く

右ペインを `transition` で出すと、React がもう一度描くのを待つぶん
**3フレーム（約50ms）止まって見えた。**
CSS の `animation` にすると、要素が出たその場から動きはじめる。

    出るときの幅（1フレームごと）
      transition: [0, 0, 0, 58, 129, 222, 303, …]
      animation : [0, 62, 141, 242, 318, 355,  …]

## 3. 何もしていないときに CPU を使わない

ホームを開いているだけで **CPU の3割**を使っていた。
オフィスの絵に粒子アバターが5つあり、その中で `<animateTransform>` が
20本回っていたため。SVG の中で回すと、その下にある**2,373個の粒**を
ブラウザが毎フレーム計算し直す。

直したのは2つ。**見た目は変えていない。**

- **層ごとに別の `<svg>` にして、CSS で回す。**
  絵は一度描くだけで済み、あとは GPU が向きを変える
- **粒が線の上を流れるのを `left` ではなく `transform` に。**
  `left` を動かすと毎フレーム置き場所を計算し直す

|  | 前 | 後 |
|---|---|---|
| `/home` | CPU 31% · レイアウト 4.2% | **CPU 5% · レイアウト 0%** |
| `/team` | CPU 8% | **CPU 0%** |
| SMIL の数 | 20本 | **0本** |

粒の数（2,373）は減らしていない。**軽くするために絵を削らない。**

---

## 動きを減らす設定の人には

`prefers-reduced-motion` で**飾りの動きだけ**止める。
回っている印と脈は「いま動いている」という事実なので残す。
出入りは 0.01ms にして、消えることは消える（中身が出ないと困る）。

## 4. 「Cloudflare が重い」は本当か — 測った

**Cloudflare のせいではなかった。** 同じビルドを workerd（Cloudflare の実行環境）と
Node で並べて測ると、差は1回あたり7〜10ms しかない。

    最初のバイトが返るまで（3回ずつ）
      /home          workerd 0.054 / 0.045 / 0.044     node 0.040 / 0.038 / 0.060
      /tasks         workerd 0.020 / 0.018 / 0.022     node 0.013 / 0.011 / 0.013
      /team          workerd 0.019 / 0.019 / 0.023     node 0.011 / 0.013 / 0.012
      /deliverables  workerd 0.023 / 0.017 / 0.017     node 0.013 / 0.009 / 0.012

遅かったのは**行き先を先に取っていなかったこと**。

### 行き先は先に取る

Next.js の既定は「行き先が毎回サーバーで作られるものなら、先には取らない」。
この会社の画面は全部そうなので、既定のままだと**押してから取りに行く**ことになる。

素の `<Link>` をやめて `components/ui/Go.tsx` に寄せた（`<Link prefetch>` を1枚かぶせただけ）。
リンクが画面に入った時点で中身を取っておくので、押した瞬間にはもう手もとにある。

    押してから中身が出るまで（ネットワークの遅延を 60ms にして測る）
      オフィスの社員 → メンバー     169ms  →  87ms
      レール → チャット             —      →  53ms
      タスクの Work列 → Work        —      →  10ms

残る 50〜90ms は**その画面の JavaScript を初めて取る往復**（15〜31KB）。
一度取れば以後は 10ms 台になる。ここから先は物理の話なので削らない。

### 認証で毎回 Supabase に行かない

`middleware.ts` が `supabase.auth.getUser()` を呼んでいた。これは**毎回、認証サーバーに
問い合わせに行く**。middleware は画面の移動だけでなく**先読みの1本1本にも走る**ので、
1画面ひらくだけで往復が数十回になる（実測: 1画面で先読み31本）。
ダミー表示の間は素通ししているので出ていなかったが、認証を入れた瞬間に効いてくる。

`getClaims()` に変えた。署名鍵を1度だけ取って**手もとで JWT を検証する**ので往復が要らない。
（鍵が共有鍵のままの間は内部で問い合わせに落ちる。**非対称鍵に切り替えたときに効く**）

## 5. 押してから反応するまで（2回目）— 中で何が起きていたか

通信を0にしても、まだ「押してから少し待つ」感じが残っていた。
**ブラウザの中で計った**（`tools/check/press.mjs`）。押してから右ペインが見えるまで、
CPU を4倍おそくして、1画面につき5回。

    直す前（4倍おそく）
      /tasks         154, 73, 59, 55, 64
      /team          268, 162, 102, 97, 131
      /hire          270, 114, 89, 106, 102

原因は2つあった。

### ① URL を先に書いていた

`history.replaceState` を呼ぶと Next.js の router が状態を作り直し、その途中で
画面の高さを読む（`dontForceLayout` のところ）。これが**ページ全体の配置計算を強制する**。
遅い機械では 40ms ほど固まる。押した瞬間に固まると「反応が遅い」になる。

**開くのは手もとの state で先にやり、URL は描き終わってから書く**ことにした。
見えるものは同じで、待たされるところだけ無くなる。

### ② 44px のアバターに300個の粒を置いていた

右ペインを開くと、その中の粒子アバター（44px）が **336個の円 / 728個の節点**を作っていた。
44px の球に300個の粒を置いても、1粒は 0.4px にしかならず、滲むだけで見えない。

1本のリングに並べる密度（`DENS`）を大きさごとに分けた。
**大きく出る 72px 以上（オフィスの絵）は触っていない** — そこは見えるので減らさない。
44〜71px だけ半分に落とし、そのぶん1粒を少し大きくした（見た目は変わらない）。

    ペインを開いたときに作る節点   728 → 520
    ペインの中の円                336 → 131

### 直したあと

    4倍おそく                       ふつう
      /tasks         158, 54, 51…    25, 16, 14, 13, 20
      /team          221, 157, 82…   70, 33, 32, 35, 31
      /hire          178, 46, 96…    37, 31, 29, 33, 37
      /deliverables  137, 9, 13…     36,  3,  4,  4,  3

**1回目だけ重い**のは、その画面のペインを初めて組み立てるから。2回目からは 3〜35ms。

### 打つのも測った

    1文字打つのにかかる時間   9〜13ms（どの画面でも）
    何もしていないとき        59〜61fps（どの画面でも）
    長く止まる処理            /team のペイン初回だけ 67ms、ほかは無し

## 測るときの注意 — GPU を切らない

`--disable-gpu` で立てた Chrome はソフトウェアで描くので、オフィスの画面が **35fps** に見える。
`--use-gl=swiftshader --enable-gpu-rasterization` で立て直すと **59fps**。
**無い問題を追いかけることになる。** 実機には GPU があるので、切って測ってはいけない。

## 6. 動きの一覧（どこで何が動くか）

**動きの言葉は1つだけ。**

    EASE      = .32s cubic-bezier(.33, 1, .68, 1)   ふつう
    EASE_FAST = .16s 同じ曲がり方                    面の明るさ・文字の色

曲線を `cubic-bezier(.32,.72,0,1)` から `cubic-bezier(.33,1,.68,1)` に替えた。
**出だしを強くしすぎない**ため。前の曲線は最初の1フレームで4割まで進むので、
「滑った」ではなく「跳んだ」に見えていた。

    レールを開いたときのパンくずの位置（1フレームごと）
      前  202, 202, 324, 368, 392, 405, 413, 419 …   ← 1フレーム目で 122px 飛ぶ
      後  202, 267, 294, 318, 339, 357, 373, 386 …   ← 均される

| どこ | 何が動くか |
|---|---|
| **左レール** | 幅 0 ↔ 260。中身は 260 のまま押し出されるので文字が畳まれない。閉じているあいだは `inert` |
| **トップバーの戻り道** | レールを閉じたときに出る印。**出したり消したりしない** — 幅を 0 にして、レールと同じ速さで開く。閉じているあいだは隙間ぶんの負の余白でパンくずが飛ばない |
| **右ペイン** | `panein` / `paneout`。閉じるときは畳み終わってから親に消してもらう |
| **入力欄** | 書いたぶんだけ滑らかに伸びる。ペインやレールの開閉に合わせて左右にも動く（幅の変化がそのまま伝わる） |
| **画面の入れ替え** | `template.tsx` ＋ `.page`。薄く沈んだところから起き上がる。**中央と右だけ**（左レールは動かさない） |
| **ペインの中身** | 別の行を選ぶ・タブを持ち替えると `.swap` で薄く重なる |
| **一覧の行** | 選ばれた面は 160ms でつく。触れたときの影は 100ms |
| **質問の板** | `.rise` — 下から上がる |
| **会社の切り替え・わたし** | `.pop` — 押した場所から開く |
| **ホームのビュー** | `key` を変えて `.rise` |

### 画面の入れ替えで透明にしない

`opacity: 0` から始めると、次の画面ができるまでの3フレームほど**中央が空に見える**。
`.35` から始めれば、薄く沈んでいるだけで消えない。

    画面が入れ替わるときの透明度（1フレームごと）
      0.35, 0.35, 0.35, 0.52, 0.75, 0.90, 0.94, 0.99, 1.00

### 入力欄の伸び方 — CSS に任せると動かせない

`field-sizing: content` を使うと JS は要らないが、高さが「決まった値」にならないので
**一瞬で変わる**（`transition` が効かない。`interpolate-size` を足しても効かない）。
滑らかに伸ばしたいので、こちらで測って高さを入れる。

ただし**打った瞬間には測らない。** 打った直後はまだ配置が決まっていないので、
そこで高さを読むとブラウザに「いますぐ全部計算しろ」と言うことになる（1文字ごとに、ページ全体を）。
次に描くタイミングまで待てば、どのみち計算されているものを読むだけで済む。
続けて打っても、待っているぶんは1回にまとめる。器には `contain: layout` を置いて、
計算がその中で済むようにする。

    入力欄が伸びるとき（1フレームごと）  26, 33, 38, 44, 48, 52, 56, 59, 61, 63, 65, 66, 68
    1文字打つのにかかる時間             10〜17ms（どの画面でも）

**0 に落として測らない。** 0 に落とすと、動き出す高さが 0 になって一瞬つぶれて見える
（`auto` にして測り、いまの高さに戻してから動かす）。
