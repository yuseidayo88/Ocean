## 変更コストの考え方

Phase 1 の報告で「あとから変えられるか」という質問をもらった。答えは領域によって違う。

| 変更コスト | 対象 | 根拠 |
|---|---|---|
| 軽い（いつでも） | 画面の見た目・配置・文言・色 | 静的な HTML/CSS。データに触らない |
| 中くらい | 画面構成、統括AIの話し方・提案の出し方 | プロンプトと画面の書き換えだけで済む |
| **重い** | **データモデル、状態遷移** | 保存済みデータの移行が要る |

だから設計は「重い側」を薄く、可変な側を厚くする。

## あとで変えたくなりそうな所（最初から可変にする）

Phase 2 の設計では、以下を**固定値としてコードに書かない**。

| 変わりそうなもの | 逃げ道 |
|---|---|
| フェーズの数（今は4） | `phases` を Work ごとの可変レコードにする。4 はデフォルトでしかない |
| AI社員の種類・人数 | `agent_definitions` はデータ。コードに職種名を書かない |
| 業種・業界 | どこにも列挙しない。Work のゴールは自由文 |
| タスクの状態の数 | 状態は文字列 enum ＋ 表示マップ。追加は1行 |
| 成果物の種類 | `kind` は文字列。ビューアはフォールバック付き |
| 使うモデル | `model_tier`（fast / standard / deep）という抽象を挟み、実モデルは設定表に置く。`ModelProvider` を1枚挟んで他社にも出られるようにする |
| トークンの換算率 | `token_rate` を設定値にする（既定 1トークン = $0.00001）。プラン変更で書き換えられる |
| 進捗率の計算式 | `progress_basis` を列に持ち、計算式を差し替えられるようにする |
| 統括AIのプロンプト | DB に版を持つ。デプロイなしで差し替え・巻き戻しができる |
| ホスティング / 実行基盤 | `AgentRunner` を1枚挟む。Vercel → Cloudflare も、自前ループ → Managed Agents も、実装を足すだけ |

## 設計の前提（Phase 0 / 1 からの持ち越し）

- **ユーザーは社長ひとり**。ゴールを言う・採用する・判断する、の3つだけをする
- **偽の進捗を出さない**。画面の状態＝バックエンドの状態。進捗率は保存された事実から導く
- **成果物は会話と分ける**。会話は経緯、成果物は資産
- **承認された決定は構造化して保存**し、以降のAI社員が必ず参照する
- **高度なAI設定は隠す**。モデルや思考量はユーザーに選ばせない
