# 06 — Work の粒度と、用事

> 「LPが最終目標の Work もあるし、LPが過程の Work もある。それって判断する？」
> これは設計の穴でした。ここで埋めます。

## 依頼が来たときの分かれ道

仕事には**3つの入れ物**があります。統括AIは、あなたの依頼を必ずこの3つのどれかに入れます。

| 入れ物 | 何か | 計画 | 承認 |
|---|---|---|---|
| **用事** | 1タスクで終わる頼みごと | なし | なし。適任の社員に振って即実行 |
| **フェーズ** | 進行中の Work の一区切り | 親の計画の一部 | 親の計画で済んでいる |
| **Work** | 終わりのある、まとまった仕事 | 立てる | **要る** |

```
新しい依頼
 │
 ├─ 1タスクで終わる？ ─── はい ──→ 【用事】担当を決めて即実行
 │        いいえ
 │         ↓
 ├─ 終わりが言える？ ──── いいえ ─→ 何ができたら終わりかを先に決める（まだ入れ物に入れない）
 │        はい
 │         ↓
 ├─ 単独で価値がある？ ── いいえ ─→ 【フェーズ】進行中の Work に入れる
 │        はい
 │         ↓
 └─ 3ヶ月以内に終わる？ ─ はい ──→ 【Work】
          いいえ ──────────────→ 分割を提案する
```

## Work の粒度は、中身では決まらない

**その先に何を期待しているかで決まります。**

| 言われたこと | LP の位置 | 入れ物 |
|---|---|---|
| 「LPを作って公開したい」 | **終着点** | Work |
| 「日本語学習サービスを立ち上げたい」 | **通過点** | Work の中のフェーズ |
| 「さっきのLPの見出しを直して」 | **部品** | 用事 |

同じ LP でも、意図が違えば入れ物が違う。だから**ルールだけでは決まりません。**

判定は3つの条件で行います。**全部そろえば Work。**

1. **終わりが言える** — 「何ができたら終わりか」が1文で書ける
2. **単独で価値がある** — それだけ完成しても意味がある。次を待たなくていい
3. **長すぎない** — 目安3ヶ月。それ以上かかるなら、途中で前提のほうが変わる

| | ① 終わり | ② 単独の価値 | ③ 長さ | 入れ物 |
|---|---|---|---|---|
| LPを作って公開したい | 公開されている | 問い合わせが来る | 2〜4週 | **Work** |
| 日本語学習サービスを立ち上げたい | サービスが動いている | ある | 10週 | **Work**（LPはフェーズ） |
| 事業を伸ばしたい | 言えない | — | 無期限 | **入れ物に入れない** |
| LPの見出しを直して | 直っている | 単独では価値がない | 1時間 | **用事** |

②が一番効きます。**「それだけ出来上がっても、まだ何も始まらない」なら、それは過程です。**

## 聞き方 — 統括AIが先に判定し、違うときだけ直してもらう

**「これは Work ですか？」とは聞きません。** 判定を済ませて、提案の形で出します。

進行中の Work があって、そこに収まりそうなときだけ、2択を出します。

```
┌────────────────────────────────────────────┐
│ 「LPと申込フォーム」は単体でも成立します。      │
│ どちらで進めますか。                          │
│                                            │
│ [ 新しい Work にする ]  ← 推奨（青）          │
│ [ 日本語学習サービス のフェーズに入れる ]       │
└────────────────────────────────────────────┘
```

- 進行中の Work がなければ**聞きません**。必ず新しい Work
- 用事だと判定したら**聞きません**。振って、やって、結果を返す
- 質問は1回、選択肢は2つ、フォームは出しません

## 用事

**Work にするほどでもない頼みごと**の置き場です。統括AIが適任のAI社員を選んで振ります。

```
あなた「この文章、もう少し短くして」
  ↓
統括AI「コンテンツライターに振りました」   ← 計画も承認もない
  ↓
コンテンツライター が実行
  ↓
返ってくる（会話の中で返す。残すべきものは成果物へ）
```

| | |
|---|---|
| 計画 | 立てない |
| 承認 | 要らない |
| フェーズ | ない |
| 担当 | 統括AIが選ぶ。指名もできる |
| 成果物 | 出れば成果物に入る。軽いものは会話で返して終わり |
| 上限 | **1件 30,000トークン**。超えそうなら止めて提案する（下記） |

### 用事が大きすぎたとき

見積もりが上限を超えそうなら、統括AIは実行前に止めます。

> 「これは用事の範囲を超えます。3日ぶんの仕事です。**Work にしますか？**」

**これが用事から Work への昇格経路**です。用事のつもりで頼んだものが本腰だと分かる瞬間は必ず来るので、
そこに道を作っておきます。

### なぜ「常設の Work」にしないのか

一度は「相談」という常設の Work を作る案を書きましたが、やめました。

- 用事に**計画も承認もフェーズも要りません**。Work の器を着せると、要らないものが全部ついてきます
- ホームの「進行中のWork」に「相談」が混ざると、**本当に進んでいる仕事が見えにくくなります**
- 「Work は終わりのあるまとまった仕事」という定義が濁ります

**入れ物を分けたほうが、両方きれいになります。**

### 画面

左レールに **用事**（Work の下、タスクの上）。時系列のリストで、1行に
依頼文 / 担当社員 / 状態 / かかったトークン。
タスク一覧では、Workごとのグループ帯と並んで **「用事」のグループ帯**として出ます。

## 間違えても直せることの方が大事

判定を完璧にする必要はありません。**あとから移せれば、最初の判断の重みが下がります。**

| 操作 | いつ起きるか |
|---|---|
| **用事 → Work に昇格** | 「思ったより大仕事だった」 |
| **フェーズ → Work に切り出す（昇格）** | 「LPを独立して追いたい」 |
| **Work → 他の Work のフェーズに畳む（降格）** | 「これは結局あの立ち上げの一部だった」 |

タスク・成果物・決定事項・実行履歴は `work_id` で紐づいているので、付け替えれば揃って移ります。
移動は `audit_events` に残します。

### 入れ子にはしません

**Work の中に Work は作りません。** 階層は **Work → フェーズ → タスク** の3段で固定。
用事は**その外側に1タスクで立つ**もので、階層ではありません。

入れ子にすると、社長が階層を管理する仕事が生まれます。それは「ゴールを示し、採用し、判断だけする」に反します。
3段で足りなくなったら、それは**Work を分けるべき合図**です。

## 大きすぎる Work は分割を提案する

計画時点で **フェーズが6つを超える**か、**見積もりが 1,000,000 トークンを超える**なら、統括AIが提案します。

> 「これは2つの Work に分けた方がいいと思います。
> 　いまの計画だと、③に入る頃には①で決めたことの前提が変わっています。」

## プラン制限との関係（正直に書いておく）

同時に進行できる Work 数でプランを分けています（Starter 2 / Pro 5）。
Work の境界をユーザーが決められる以上、**この制限はすり抜けられます**（全部1つの Work に詰め込む）。
用事には Work 数の制限をかけません（かけると「気軽に頼む」が壊れます）。

ただし詰め込むと、この製品の価値である「進み具合が一目で分かる」が消えます。
**Work 数の制限は組織の目安であって、課金の壁はトークンです。** そこは分けて考えます。

## データモデルへの影響

| テーブル | 変更 | 意味 |
|---|---|---|
| `tasks` | `work_id` を **nullable** に | null なら用事 |
| `tasks` | `phase_id` も nullable | 用事にフェーズはない |
| `tasks` | `kind` を追加 | `work_task` / `errand` |
| `works` | `origin_id` / `origin_kind` | 昇格して切り出された元（フェーズ or 用事） |
| `phases` | `promoted_to_work_id` | 昇格の対応を両方向から辿れるように |

不変条件を差し替えます。

> **7.（旧）すべてのタスクは Work に属する**
> **7.（新）タスクは `kind='work_task'`（`work_id` と `phase_id` を持つ）か、
> 　　　　`kind='errand'`（どちらも null）のどちらかであり、中間の状態を取らない。**
