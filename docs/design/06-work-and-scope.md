# 06 — Work の粒度

> 「LPが最終目標の Work もあるし、LPが過程の Work もある。それって判断する？」
> これは設計の穴でした。ここで埋めます。

## 依頼が来たときの分かれ道

仕事の入れ物は**2つ**です。統括AIは、あなたの依頼を必ずどちらかに入れます。

| 入れ物 | 何か | 計画 | 承認 |
|---|---|---|---|
| **フェーズ** | 進行中の Work の一区切り | 親の計画の一部 | 親の計画で済んでいる |
| **Work** | 終わりのある、まとまった仕事 | 立てる | **要る** |

そして、それより小さい頼みごとは**いまある Work の中のタスク**になります。
タスクは入れ物ではなく、Work の中身です。

```
新しい依頼
 │
 ├─ 終わりが言える？ ──── いいえ ─→ 何ができたら終わりかを先に決める（まだ入れ物に入れない）
 │        はい
 │         ↓
 ├─ 単独で価値がある？ ── いいえ ─→ 進行中の Work の中へ
 │        はい                    （その Work の【フェーズ】か、フェーズの中の【タスク】）
 │         ↓
 └─ 3ヶ月以内に終わる？ ─ はい ──→ 【Work】
          いいえ ──────────────→ 分割を提案する
```

## Work の粒度は、中身では決まらない

**その先に何を期待しているかで決まります。**

| 言われたこと | LP の位置 | 入れ物 |
|---|---|---|
| 「LPを作って公開したい」 | **終着点** | Work |
| 「日本語学習サービスを立ち上げたい」 | **通過点** | Work の中のフェーズ |
| 「さっきのLPの見出しを直して」 | **部品** | その LP を持つ Work の中のタスク |

同じ LP でも、意図が違えば入れ物が違う。だから**ルールだけでは決まりません。**

判定は3つの条件で行います。**全部そろえば Work。**

1. **終わりが言える** — 「何ができたら終わりか」が1文で書ける
2. **単独で価値がある** — それだけ完成しても意味がある。次を待たなくていい
3. **長すぎない** — 目安3ヶ月。それ以上かかるなら、途中で前提のほうが変わる

| | ① 終わり | ② 単独の価値 | ③ 長さ | 入れ物 |
|---|---|---|---|---|
| LPを作って公開したい | 公開されている | 問い合わせが来る | 2〜4週 | **Work** |
| 日本語学習サービスを立ち上げたい | サービスが動いている | ある | 10週 | **Work**（LPはフェーズ） |
| ロゴを作りたい | 出来上がっている | ある | 3日 | **Work**（小さくてよい） |
| 事業を伸ばしたい | 言えない | — | 無期限 | **入れ物に入れない** |
| LPの見出しを直して | 直っている | 単独では価値がない | 1時間 | **Work の中のタスク** |

②が一番効きます。**「それだけ出来上がっても、まだ何も始まらない」なら、それは過程です。**

## 聞き方 — 統括AIが先に判定し、違うときだけ直してもらう

**「これは Work ですか？」とは聞きません。** 判定を済ませて、提案の形で出します。

進行中の Work があって、そこに収まりそうなときだけ、2択を出します。

```
┌────────────────────────────────────────────┐
│ 「LPと申込フォーム」は単体でも成立します。      │
│ どちらで進めますか。                          │
│                                            │
│ [ 新しい Work にする ]  ← 推奨（青）          │
│ [ 日本語学習サービス のフェーズに入れる ]       │
└────────────────────────────────────────────┘
```

- 進行中の Work がなければ**聞きません**。必ず新しい Work
- **タスクで済むと判定したら聞きません。** どの Work に入れたかだけ言って、振って、実行する
- 質問は1回、選択肢は2つ、フォームは出しません

## 判断ログ — 「用事」をやめた（2026年8月）

以前は入れ物が3つあり、3つ目に**用事**（1タスクで終わる頼みごと。計画も承認もなく、
Work の外側に1タスクで立つ）を置いていました。**やめました。**

### やめた理由

1. **社長が覚える言葉が1つ増える。** 「これは Work、これは用事」を人間が意識した瞬間に、
   「ゴールを示し、判断だけする」ではなくなります
2. **どの画面でも例外になる。** タスク一覧では Work 列に「用事」という Work ではないものが入り、
   進捗のタイムラインでは Work のレーンの下に用事だけのレーンがぶら下がり、
   ワークフローでは繋がらないノードが浮く。**1つの概念のために、全部の画面に but が付きます**
3. **データにも例外が要る。** `tasks.work_id` を nullable にして
   「work_task なら Work を持ち、errand なら持たない」という制約を1本足していました。
   これは「すべてのタスクは Work に属する」という一番単純な不変条件を壊すためだけの制約です
4. **本当に必要な逃げ道は、もう別にある。** 小さい頼みごとの行き先は
   **いまある Work の中のタスク**です。LPの見出しを直したいなら、その LP を持つ Work があります

### 代わりにどうするか

- **小さい頼みごとは、いちばん近い Work のタスクにする。** 統括AIが Work を選び、
  「LPと申込フォーム に入れました」とだけ言って実行する。計画も承認も要りません
- **合う Work が1つも無いなら、それは小さくても Work です。**
  「ロゴを作りたい」は3条件（終わりが言える / 単独で価値がある / 短い）を全部満たします。
  そういうものは Work にして構いません。フェーズ1つ・タスク数個の Work になるだけです

### 失うもの（正直に）

**承認が1回増える場面があります。** 進行中の Work がまったく無い状態で
「ちょっとこれ調べて」と頼むと、以前は即実行でしたが、いまは小さい Work の承認が1回はさまります。

その代わり、**画面もデータも例外がゼロ**になります。
入れ物が2つで済み、すべてのタスクが Work に属し、タイムラインに浮いたレーンが無くなる。
その交換なら得だと判断しました。

## 間違えても直せることの方が大事

判定を完璧にする必要はありません。**あとから移せれば、最初の判断の重みが下がります。**

| 操作 | いつ起きるか |
|---|---|
| **タスク → Work に切り出す（昇格）** | 「思ったより大仕事だった」 |
| **フェーズ → Work に切り出す（昇格）** | 「LPを独立して追いたい」 |
| **Work → 他の Work のフェーズに畳む（降格）** | 「これは結局あの立ち上げの一部だった」 |

タスク・成果物・決定事項・実行履歴は `work_id` で紐づいているので、付け替えれば揃って移ります。
移動は `audit_events` に残します。

### Work から Work が生まれる

判断やフェーズの完了をきっかけに、**新しい Work が生まれる**ことがあります。

> 「価格が決まりました。**LPと申込フォーム**は別の Work にしましょう。
> 　ターゲットも決まったので、**SNS運用の立ち上げ**も並行して始められます。」

これは入れ子ではありません。**新しい Work は横に並ぶ兄弟**で、`origin_phase_id` に
「どのフェーズから生まれたか」だけを残します。

ワークフロー画面では、ここが**枝分かれ**として見えます。線の上の小さい文字で区別します。

| ラベル | 意味 |
|---|---|
| **次のフェーズ** | この Work の続き。同じ計画の中 |
| **新しい Work** | ここから独立して動きだす別の Work |

枝分かれしても、**それぞれの Work は Work → フェーズ → タスク の3段のまま**です。

### 入れ子にはしません

**Work の中に Work は作りません。** 階層は **Work → フェーズ → タスク** の3段で固定。

入れ子にすると、社長が階層を管理する仕事が生まれます。それは「ゴールを示し、採用し、判断だけする」に反します。
3段で足りなくなったら、それは**Work を分けるべき合図**です。

## 大きすぎる Work は分割を提案する

計画時点で **フェーズが6つを超える**か、**見積もりが 1,000,000 トークンを超える**なら、統括AIが提案します。

> 「これは2つの Work に分けた方がいいと思います。
> 　いまの計画だと、③に入る頃には①で決めたことの前提が変わっています。」

## プラン制限との関係（正直に書いておく）

同時に進行できる Work 数でプランを分けています（Starter 2 / Pro 5）。
Work の境界をユーザーが決められる以上、**この制限はすり抜けられます**（全部1つの Work に詰め込む）。

ただし詰め込むと、この製品の価値である「進み具合が一目で分かる」が消えます。
**Work 数の制限は組織の目安であって、課金の壁はトークンです。** そこは分けて考えます。

## データモデル

| テーブル | 形 | 意味 |
|---|---|---|
| `tasks` | `work_id` **NOT NULL** | すべてのタスクは Work に属する |
| `tasks` | `phase_id` は nullable | Work 直下のタスク（どのフェーズにも入れないもの）を許す |
| `works` | `origin_phase_id` | 切り出された元のフェーズ |
| `phases` | `promoted_to_work_id` | 昇格の対応を両方向から辿れるように |

不変条件7は、いちばん単純な形に戻りました。

> **7. すべてのタスクは Work に属する。**（`tasks.work_id` NOT NULL）
