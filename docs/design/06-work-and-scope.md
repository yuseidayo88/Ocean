# 06 — Work の粒度

> 「LPが最終目標の Work もあるし、LPが過程の Work もある。それって判断する？」
> これは設計の穴でした。ここで埋めます。

## 中身では決まらない。**その先に何を期待しているか**で決まる

| 言われたこと | LP の位置 | 粒度 |
|---|---|---|
| 「LPを作って公開したい」 | **終着点** | Work |
| 「日本語学習サービスを立ち上げたい」 | **通過点** | Work の中のフェーズ |
| 「さっきのLPの見出しを直して」 | **部品** | タスク |

**同じ成果物でも、意図が違えば粒度が違う。だからルールだけでは決まりません。決めるのはあなたです。**
ただし毎回聞かれるのは邪魔なので、**統括AIが先に判定して提案し、違うときだけ直してもらう**形にします。

## 統括AIが使う判定条件

3つ**全部**当てはまれば Work。1つでも欠ければフェーズかタスク。

1. **終わりが言える** — 「何ができたら終わりか」が1文で書ける
2. **単独で価値がある** — それだけ完成しても意味がある。次を待たなくていい
3. **長すぎない** — 目安3ヶ月。それ以上かかるなら、途中で前提のほうが変わる

| | ① 終わり | ② 単独の価値 | ③ 長さ | 判定 |
|---|---|---|---|---|
| LPを作って公開したい | 公開されている | 問い合わせが来る | 2〜4週 | **Work** |
| 日本語学習サービスを立ち上げたい | サービスが動いている | ある | 10週 | **Work**（LPはその中のフェーズ） |
| 事業を伸ばしたい | 言えない | — | 無期限 | **Work にしない**。何を伸ばすか先に決める |
| LPの見出しを直して | 直っている | 単独では価値がない | 1時間 | **タスク** |

②が一番効きます。**「それだけ出来上がっても、まだ何も始まらない」なら、それは過程です。**

## 聞き方

進行中の Work があって、そこに収まりそうなときだけ聞きます。1回、2択、フォームなし。

```
┌────────────────────────────────────────────┐
│ 「LPと申込フォーム」は単体でも成立します。      │
│ どちらで進めますか。                          │
│                                            │
│ [ 新しい Work にする ]  ← 推奨（青）          │
│ [ 日本語学習サービス のフェーズに入れる ]       │
└────────────────────────────────────────────┘
```

進行中の Work がなければ**聞きません**。必ず新しい Work にします。

## 間違えても直せることの方が大事

判定を完璧にする必要はありません。**あとから移せれば、最初の判断の重みが下がります。**

| 操作 | いつ起きるか |
|---|---|
| **フェーズ → Work に切り出す（昇格）** | 「LPが思ったより大仕事になった。独立して追いたい」 |
| **Work → 他の Work のフェーズに畳む（降格）** | 「これは結局あの立ち上げの一部だった」 |

一緒に動くもの: タスク・成果物・決定事項・実行履歴。すべて `work_id` を持っているので、付け替えれば揃って移ります。
`audit_events` に移動を残し、`works.origin_phase_id` に「どこから切り出したか」を残します。

### 入れ子にはしません

**Work の中に Work は作りません。** 階層は **Work → フェーズ → タスク の3段で固定**です。

入れ子にすると、社長が階層を管理する仕事が生まれます。それは「ゴールを示し、採用し、判断だけする」に反します。
3段で足りなくなったら、それは**Work を分けるべき合図**です。

## Work に属さない依頼

ホームの「統括AIに指示する」から出る単発の相談 —「この文章直して」「競合1社だけ調べて」。

**「相談」という常設の Work を会社に1つ持ちます**（`works.kind = 'inbox'`、削除不可）。単発はここに入ります。
これで「すべてのタスクは Work に属する」という不変条件を壊さずに済みます。

相談の中で話が育ったら、統括AIが「これ、Work にしましょうか」と提案します。

## 大きすぎる Work の検出

計画を立てた時点で、**フェーズが6つを超える**か、**見積もりが 1,000,000 トークンを超える**なら、
統括AIは分割を提案します。

> 「これは2つの Work に分けた方がいいと思います。
> 　いまの計画だと、③に入る頃には①で決めたことの前提が変わっています。」

## プラン制限との関係（正直に書いておく）

同時に進行できる Work 数でプランを分けています（Starter 2 / Pro 5）。
Work の境界をユーザーが決められる以上、**この制限はすり抜けられます**（全部1つの Work に詰め込む）。

ただし詰め込むと、この製品の価値である「進み具合が一目で分かる」が消えます。
**Work 数の制限は組織の目安であって、課金の壁はトークンです。** そこは分けて考えます。

## データモデルへの追加

| テーブル | 列 | 意味 |
|---|---|---|
| `works` | `kind` | `normal` / `inbox`（常設の「相談」） |
| `works` | `origin_phase_id` | 昇格して切り出されたとき、元のフェーズ |
| `phases` | `promoted_to_work_id` | 降格・昇格の対応を両方向から辿れるように |

不変条件を1つ足します。

> **7. `works.kind='inbox'` の Work は会社に必ず1つだけ存在し、削除できない。**
